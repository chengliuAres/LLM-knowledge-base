# 智能 SDD 编排器

将 **OpenSpec**（规范治理——"做什么"和"为什么"）与 **Superpowers**（工程执行——"怎么做"）融合为一个闭环编排工作流。目标：规范即唯一真相源 + 工程纪律闭环。杜绝 Vibe Coding、规范漂移、未测试代码和返工。

## 为什么需要这个 Skill

缺乏编排时，开发者面临两种失败模式：
1. **有规范无纪律** —— 文档写得漂亮，代码一塌糊涂
2. **有纪律无规范** —— 代码测试充分，但解决的是错误的问题

本 Skill 弥合这道裂缝：OpenSpec 确保你做的是*正确的事*；Superpowers 确保你*正确地做事*。

## 阶段 0：环境就绪检查 + 决策框架

在采取任何行动之前，先确保工具链就绪，再选择正确路径。

### 环境就绪检查

按顺序检查以下条件，缺失则自动修复：

1. **OpenSpec CLI 是否可用？**
   - 运行 `which openspec`
   - 如果未找到：提示用户安装（`npm install -g openspec`），等待安装完成后继续

2. **当前项目是否已初始化 OpenSpec？**
   - 检查项目根目录是否存在 `openspec/config.yaml`
   - 如果不存在：自动运行 `openspec init`，使用默认配置初始化
   - 初始化后确认 `openspec/` 目录结构已生成

3. **OpenSpec Skills 是否已安装？**
   - 检查 `.claude/skills/` 下是否存在 `openspec-*` 目录（至少应有 `openspec-propose`）
   - 如果缺失：检查项目中是否有 `.claude/commands/opsx/` 作为替代
   - 如果两者都缺失：提示用户安装 OpenSpec Skills（`openspec skills install`），因为本 Skill 依赖 `/opsx:propose`、`/opsx:archive` 等命令

4. **Superpowers 是否可用？**
   - 检查可用 Skills 列表中是否包含 `superpowers:brainstorming`、`superpowers:writing-plans` 等核心技能
   - 如果缺失：提示用户安装 Superpowers 插件

5. **Git 仓库是否就绪？**
   - 运行 `git status` 确认当前目录在 Git 仓库内
   - 如果不是 Git 仓库：提示用户初始化（`git init`）或切换到正确目录

所有检查通过后，输出简要就绪确认（一行即可），然后进入决策框架。

### 决策问题

| 问题 | 选项 | 影响 |
|------|------|------|
| **需求清晰度** | 模糊的业务想法 → 完整流水线。已有明确规范 → 跳到阶段 2 | 决定是否需要头脑风暴 |
| **变更类型** | 全新功能（0→1）· 存量修改（Brownfield）· 热修复（紧急 Bug） | 决定 OpenSpec 深度 |
| **复杂度** | 高（规则引擎、实时计算、多租户、性能约束）· 中 · 低 | 决定哪些步骤可以合并 |
| **是否需要可追溯性？** | 几乎总是需要 → 必须执行 OpenSpec 归档 | 决定阶段 3 |

### 路径选择

```
┌──────────────────────────────────────────────────────────┐
│                      决策矩阵                              │
├──────────────────┬───────────────────┬────────────────────┤
│ 全新功能（0→1）   │ 存量增量修改       │ 热修复 / 小修补     │
├──────────────────┼───────────────────┼────────────────────┤
│ 完整流水线：      │ 增量流水线：       │ 精简流水线：        │
│ 头脑风暴 →       │ 增量提案 →         │ 简化提案 →         │
│ 完整提案 →       │ 增量规范           │ 定向 TDD →         │
│ 完整规范 →       │ (ADDED/MODIFIED/  │ 归档               │
│ 原子计划 →       │  REMOVED) →       │                    │
│ TDD → 审查 →     │ 定向计划 →         │                    │
│ 验证 → 归档      │ TDD → 审查 →      │                    │
│                  │ 验证 → 归档        │                    │
└──────────────────┴───────────────────┴────────────────────┘
```

### 输出你的决策

在继续之前，必须声明：
1. **路径**：完整 / 增量 / 精简
2. **理由**：2-3 句话
3. **预计阶段数**：几个主要阶段

### 路径升级机制

如果在执行过程中发现当前路径不足以覆盖变更范围，允许升级：
- **精简 → 增量**：热修复调查中发现 bug 根因涉及多处逻辑变更，需升级为增量流水线。回到阶段 1 创建增量提案。
- **增量 → 完整**：增量修改过程中发现需要重新设计整个模块，需升级为完整流水线。回到阶段 1 进行头脑风暴。
- 升级时必须通知用户并获得确认。

## 阶段 1：OpenSpec 规范治理（"做什么"）

本阶段建立唯一真相源。根据决策路径选择正确的 OpenSpec 命令。

### 全新功能（完整流水线）

1. **先做头脑风暴** —— 调用 `superpowers:brainstorming` 探索意图、提出澄清问题、产出设计文档。这在 OpenSpec 之前执行，因为头脑风暴可能重塑整个方案。

2. **创建提案** —— 调用 `/opsx:propose <变更名称>` 生成：
   - `proposal.md` —— 业务价值、变更理由、非功能需求、边缘案例
   - `specs/<能力>/spec.md` —— 包含场景的详细需求
   - `design.md` —— 技术方案
   - `tasks.md` —— 实现任务

3. **用户审阅提案** —— 呈交提案等待批准。未经确认不得继续。
   - 如果用户拒绝：收集反馈意见，修改提案后重新提交审阅。如果用户要求根本性调整，回到头脑风暴阶段重新探索。

### 存量修改（增量流水线）

1. **先探索现有代码** —— 使用 `/opsx:explore` 在提出变更前调查当前实现。

2. **创建增量提案** —— 调用 `/opsx:propose <变更名称>`。在规范中使用增量标记：
   - `ADDED` —— 新增需求
   - `MODIFIED` —— 修改的需求（展示变更前后对比）
   - `REMOVED` —— 废弃的需求

3. **用户审阅增量** —— 确认范围正确，无意外副作用。
   - 如果用户拒绝：收集反馈，修改增量提案后重新提交。如果发现范围远超预期，回到探索阶段重新评估。

### 热修复（精简流水线）

1. **简化提案** —— 调用 `/opsx:propose <变更名称>`，范围最小化。提案可以简短，但必须存在以保证可追溯性。

2. **快速确认** —— 在实现前获得用户签字同意。
   - 如果用户拒绝：收集反馈，修改提案后重新提交。

### 领域特定约束

对于复杂业务领域（如广告技术、金融科技、医疗健康），提案必须明确说明：
- **安全不变量** —— 什么绝对不能发生？（如：预算超支、数据泄露）
- **一致性规则** —— 多租户隔离、事务边界
- **实时约束** —— 延迟预算、吞吐量要求
- **监控钩子** —— 生产环境中需要观测什么

## 阶段 2：Superpowers 工程执行（"怎么做"）

规范获批后，切换到工程执行。OpenSpec 的 `tasks.md` 成为 Superpowers 计划的输入。

### 步骤 2.1：制定计划

如果阶段 1 已完成头脑风暴，直接以其产出作为输入；如果选择的是增量或精简流水线（无头脑风暴），则在制定计划前先快速确认需求边界。

以 OpenSpec 产物为上下文，调用 `superpowers:writing-plans`：
- 阅读 `proposal.md`、`specs/`、`design.md`、`tasks.md`
- 将每个 OpenSpec 任务拆解为 2-5 分钟的原子微任务
- 每个微任务必须包含：精确文件路径、完整代码、测试命令、预期输出

### 步骤 2.2：隔离环境

调用 `superpowers:using-git-worktrees` 创建隔离的开发环境。绝不在主分支上直接开发。

### 步骤 2.3：执行

根据任务独立性选择执行策略：

- **独立任务** → `superpowers:subagent-driven-development`（并行执行，每个任务一个干净的子代理，两阶段审查）
- **串行/依赖任务** → `superpowers:executing-plans`（内联执行，带检查点的批处理）

执行期间，以下 Superpowers 技能为**强制要求**（不可选）：

| 技能 | 何时使用 | 不可绕过？ |
|------|----------|-----------|
| `superpowers:test-driven-development` | 每个任务 | 是 —— Red → Green → Refactor，始终执行 |
| `superpowers:systematic-debugging` | 任何失败 | 是 —— 先找根因再修复 |
| `superpowers:verification-before-completion` | 标记完成前 | 是 —— 先有证据再下结论 |
| `superpowers:requesting-code-review` | 每个任务完成后 | 是 —— 规范符合性 + 代码质量 |
| `superpowers:receiving-code-review` | 收到反馈时 | 是 —— 技术严谨，拒绝表演式认同 |

### 步骤 2.4：验证规范符合性

所有任务完成后，运行 `/opsx:verify` 确认实现与已批准规范一致。这能捕获规范与代码之间的漂移。

如果验证失败：修改代码（而非规范），除非规范本身有误——此时先更新规范、获得批准，再修改代码。

---

## 阶段 3：闭环收尾

### 步骤 3.1：完成分支

调用 `superpowers:finishing-a-development-branch`：
- 运行完整测试套件
- 呈现选项：合并、创建 PR、保留、丢弃
- 清理 worktree

### 步骤 3.2：归档变更

调用 `/opsx:archive <变更名称>`：
- 将变更移至带日期前缀的归档目录
- 将增量规范同步到主规范（唯一真相源）
- 生成历史追溯记录

此步骤为**强制要求**。未归档的变更会导致规范漂移。

### 步骤 3.3：交付总结

输出简要总结：
- 创建/修改的文件（数量）
- 测试覆盖（新增测试数）
- 已归档的规范产物
- 待跟进事项（如有）

## 铁律

无论选择何种路径或复杂度，以下规则不可绕过：

1. **TDD 不可商量** —— 没有失败的测试就不写生产代码
2. **完成前必须验证** —— 运行命令、阅读输出、确认成功
3. **合并后必须归档** —— 每个已完成的变更都要归档以维护唯一真相源
4. **规范高于代码** —— 如果代码偏离规范，修改代码（或先经批准更新规范）
5. **存量修改 = 增量** —— 始终检查现有代码；使用增量标记精准修改
6. **用户批准提案** —— 绝不跳过阶段 1 与阶段 2 之间的审批关卡

## 错误恢复

如果任何阶段失败：
1. **规范创建失败** → 使用 `/opsx:explore` 重新审视需求，重试（最多 3 次，之后暂停并请用户介入）
2. **TDD 期间测试失败** → 调用 `superpowers:systematic-debugging`，找到根因（最多 3 轮调试-修复-验证循环，之后暂停并请用户介入）
3. **审查发现严重问题** → 修复问题，重新验证，不可跳过
4. **验证失败** → 不可声称已完成。调试。修复。重新验证。（最多 3 次重试，之后暂停并请用户介入）
5. **归档冲突** → 使用 `/opsx:sync` 解决，然后重新归档
